## Почему Supabase

- Бесплатный тариф и e-mail-аутентификация из коробки, без собственного сервера.
- Postgres + **Row Level Security**: изоляция пользователей обеспечивается базой, а не доверием к клиенту.
- PostgREST даёт идемпотентные upsert (`on_conflict` + `Prefer: resolution=…`) и инкрементальные выборки обычным HTTP. Клиенту хватает OkHttp, SDK не нужен.
- Открытый исходный код: при необходимости Supabase поднимается у себя (self-hosted) с тем же клиентом.
- Backend заменяем: приложение знает только интерфейсы `AuthBackend` и `SyncBackend` (`data/sync/SyncBackend.kt`). Например, `FirebaseBackend` реализует те же методы.

## Настройка (≈10 минут)

1. Зарегистрируйтесь на https://supabase.com → **New project**. Задайте пароль БД, выберите регион поближе.
2. **SQL Editor → New query** → вставьте содержимое [`supabase/schema.sql`](supabase/schema.sql) → **Run**. Скрипт можно запускать повторно.
3. **Authentication → Sign In / Providers → Email**: провайдер включён.
   - Если «Confirm email» включено, после регистрации нужно открыть письмо, а затем войти. Приложение об этом сообщит.
   - Для быстрой проверки подтверждение можно выключить.
4. **Project Settings → API** (Data API / API Keys): скопируйте
   - **Project URL** — `https://<ref>.supabase.co`;
   - **anon / public** key.
   Ключ `service_role` в приложение **не добавляйте никогда**.
5. В корне проекта, в `local.properties` (в `.gitignore`, в Git не попадает):
   ```properties
   supabase.url=https://<ref>.supabase.co
   supabase.anonKey=<anon public key>
   ```
   или переменные окружения `SUPABASE_URL` / `SUPABASE_ANON_KEY` (например, для CI).
6. `./gradlew assembleDebug` и установите APK. Значения попадают в `BuildConfig`.
7. В приложении: **Настройки → Облачная синхронизация** → e-mail и пароль (≥6 символов) → «Создать аккаунт» или «Войти» → включите **«Синхронизировать мои данные»**. Это явное согласие на отправку координат. Сразу запустится первая синхронизация.
8. Проверка: Supabase → **Table Editor** → таблицы `tracks`, `location_points`, `explored_cells` заполнились. На втором телефоне войдите в тот же аккаунт — данные подтянутся.

anon-ключ публичный по замыслу Supabase: доступ к данным ограничивают RLS-политики. Тем не менее он хранится вне Git, чтобы проект не был привязан к чужому backend.

## Протокол

### Данные на сервере
`tracks`, `location_points`, `explored_cells`. Каждая строка содержит `user_id`, первичные ключи включают `user_id`. Каждая вставка или фактическое изменение получает `seq` из общей последовательности (триггер). По `seq` устройства инкрементально забирают изменения.

### Раунд синхронизации (`SyncEngine.run`)
1. **Push** (локальные строки с `sync_state = PENDING`):
   - маршруты пачками по 200 (`resolution=merge-duplicates`). Отмечаются выгруженными, только если `updated_at` не изменился за время отправки;
   - точки пачками по 1000 (`ignore-duplicates`), только у уже выгруженных завершённых маршрутов (внешний ключ на сервере);
   - ячейки пачками по 2000 (`merge-duplicates`, сервер оставляет более ранний `first_visited_at`).
   Активный (записываемый) маршрут выгружается после остановки записи. Территория выгружается сразу.
2. **Pull** для каждой таблицы: `GET …?user_id=eq.<uid>&seq=gt.<курсор>&order=seq.asc&limit=1000` до пустой страницы. Страница применяется локально в транзакции **вместе** с продвижением курсора, поэтому прерванный раунд продолжается с того же места, а данные не скачиваются повторно.

### Конфликты (детерминированные)
| Сущность | Правило |
|---|---|
| Маршрут | last-writer-wins по `updated_at` (на клиенте и в триггере сервера). Локальный ACTIVE-маршрут не перезаписывается |
| Точка | неизменяема: одинаковый id — одна и та же точка, дубликаты игнорируются |
| Ячейка | множество, которое только растёт: объединение, `first_visited_at` = минимум |
| Статистика маршрута | после приёма точек пересчитывается по фактическим точкам |
| Точки пришли раньше своего маршрута | создаётся заглушка маршрута с `updated_at = 0`, которую вытеснит настоящая строка |

Все операции идемпотентны: повтор запроса или раунда не создаёт дубликатов (тесты `repeated sync…`, `interrupted sync resumes without duplicating anything`).

### Надёжность
- OkHttp: connect 15 с, read/write 30 с, весь вызов 60 с.
- Повторы внутри раунда: сетевые ошибки, HTTP 5xx и 429 — до 3 попыток с экспоненциальной задержкой 1 → 2 с. 4xx не повторяются.
- WorkManager: периодически раз в ~6 ч (сеть, при желании только Wi-Fi, достаточно места) и разово после остановки записи. Временные ошибки → `Result.retry()` с экспоненциальной задержкой от 30 с, до 5 попыток.
- Токены: access-токен обновляется заранее (за 60 с до истечения) и повторно при HTTP 401. Если refresh не удался, сессия удаляется, и UI просит войти снова.
- Статус (последний успех, последняя попытка, текст ошибки, сколько ждёт отправки) хранится в `sync_metadata` и показан на экране облака.

### Аккаунт и приватность
- Без включённого переключателя «Синхронизировать мои данные» ничего не отправляется (`SyncDataUseCase`).
- При входе в **другой** аккаунт все локальные данные помечаются как неотправленные, а курсоры сбрасываются: данные загрузятся в новый аккаунт, чужие курсоры не используются.
- **Выйти** — локальный выход, синхронизация выключается.
- **Удалить мои данные из облака** — `DELETE` всех строк пользователя; локальные данные сохраняются и помечаются неотправленными, синхронизация выключается.
- **Удалить аккаунт** — RPC `delete_user()` удаляет пользователя из `auth.users`, строки удаляются каскадно.
- Токены хранятся зашифрованными ключом Android Keystore.

## Ограничения бесплатного тарифа Supabase

Актуальные лимиты: https://supabase.com/pricing. Ориентиры на момент разработки:
- **База 500 МБ.** Ячейка занимает ≈60–100 байт с индексами, точка ≈150 байт. 1 млн ячеек (≈30 км² при 5,6×3,2 м) — порядка 100 МБ.
- **Проект приостанавливается после ~7 дней без активности.** Его нужно «разбудить» в панели. Данные не теряются.
- Лимиты исходящего трафика и числа активных пользователей для личного использования несущественны.
- Встроенная отправка писем подтверждения ограничена по частоте. Для массовой регистрации нужен свой SMTP.

## Известные ограничения
- Работа с настоящим проектом Supabase не проверена (см. «Статус»).
- Курсор по `seq`: если транзакция с меньшим `seq` фиксируется позже, чем другое устройство уже прочитало бо́льший `seq` (две параллельные выгрузки в одно и то же мгновение), такая строка этим устройством пропускается, пока не изменится снова. Для одного пользователя на 2–3 устройствах это маловероятно. Кнопки полной ресинхронизации (сброса курсоров) в MVP нет. Её даёт импорт в режиме «Заменить» на этом устройстве.
- Удаление отдельных маршрутов (и их tombstones) не реализовано.
