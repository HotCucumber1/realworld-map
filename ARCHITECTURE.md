# Архитектура World Explorer

## Слои и модули

```
┌──────────────────────────────── app ────────────────────────────────┐
│ feature/{onboarding,map,history,settings,backup,sync}               │
│   Composable (stateless) ◄── StateFlow<UiState> ── ViewModel        │
│                              events ──────────────►   │            │
│ core/map      MapLibre-адаптер (ExplorationMapController,           │
│               GeoJsonWriter, FogTexture, MapStyles)                 │
│ tracking/     TrackingService (FGS location), TrackingServiceController│
│ di/           Hilt: SupabaseConfig из BuildConfig, ApplicationScope │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ use cases + интерфейсы репозиториев
┌──────────────────────────────▼─ domain (pure Kotlin/JVM) ──────────┐
│ model/  repository/ (интерфейсы)  usecase/                           │
│ geo/    ExplorationGrid, ExploredGeometryBuilder, GeoMath, GeoBounds │
│ filter/ LocationFilter(+Config)   tracking/ TrackRecorder, политика  │
│ result/ AppResult, AppError (типизированные ошибки)                  │
└──────────────────────────────▲──────────────────────────────────────┘
                                │ реализует интерфейсы
┌───────────────────────────────┴──────── data (Android library) ─────┐
│ database/ Room: entities, DAO, ExplorationStore, миграции            │
│ repository/ TrackRepositoryImpl, ExplorationRepositoryImpl           │
│ settings/  DataStore     location/ Fused/LocationManager, сеть, GPS  │
│ backup/    BackupWriter, BackupReader (валидация), BackupImporter    │
│ sync/      SupabaseBackend (OkHttp), SyncEngine, SyncRepositoryImpl, │
│            SyncWorker + WorkManagerSyncScheduler, KeystoreSessionStore│
└──────────────────────────────────────────────────────────────────────┘
```

**Dependency Rule** обеспечивается системой сборки: `domain` — JVM-модуль без Android-зависимостей. Из внешнего в домене только `kotlinx-coroutines-core` и `javax.inject` (аннотации). Модуль `app` зависит от `data` только ради Hilt-графа. ViewModel'и работают с use cases и доменными интерфейсами, к Room, GPS API и HTTP напрямую не обращаются.

**MVVM / UDF.** Каждый экран: immutable `data class …UiState` → `StateFlow` во ViewModel → stateless Composable; действия пользователя передаются вызовами методов (или `SettingsEvent`). Одноразовые события (snackbar, запрос разрешений) идут через `Channel`. Тексты ViewModel отдаёт как `UiText` и не трогает ресурсы, поэтому ViewModel тестируются на JVM.

**Почему три модуля, а не двенадцать.** Предложенная разбивка `core/*`, `feature/*` выражена пакетами внутри модулей. Отдельный модуль `domain` даёт главное — компилятор гарантирует независимость бизнес-логики. Дальнейшее дробление на MVP только увеличило бы конфигурацию сборки.

## Ключевые решения

| Решение | Почему |
|---|---|
| **MapLibre Native Android 13.7.1** вместо osmdroid | osmdroid архивирован (GitHub, ноябрь 2024). MapLibre активно развивается (BSD-2), рисует векторные тайлы на GPU, поддерживает GeoJSON-источники, fill/line/circle-слои, fill-pattern, line-blur и выражения по zoom — этого достаточно для настоящей маски тумана. |
| **OpenFreeMap** по умолчанию | Бесплатные векторные тайлы OSM без ключа и регистрации. Растровый OSM — запасной стиль (с соблюдением tile policy). Свой стиль по URL позволяет подключить любого провайдера. |
| **Fused Location Provider**, fallback на `LocationManager` | Fused лучше по точности и батарее. На устройствах без Google Play services автоматически используется GPS/Network провайдер. |
| **Supabase** (Postgres + GoTrue + PostgREST) через OkHttp | Бесплатный тариф, e-mail-аутентификация, Row Level Security на уровне БД, открытый исходный код (можно поднять у себя). Чистый REST без SDK: меньше зависимостей, клиент полностью тестируется MockWebServer. |
| **Room** — единственный источник истины | Транзакции объединяют точку, статистику трека и ячейки. Инвалидация Flow даёт реактивный UI. |
| **Типизированные ошибки** `AppResult/AppError` | Ожидаемые сбои (нет разрешения, сети, повреждённый backup) — значения, а не исключения. UI переводит их в понятные сообщения (`Formatters.error`). |

## Модель данных (Room, схема v1, `data/schemas/…/1.json`)

| Таблица | Назначение | Ключи и индексы |
|---|---|---|
| `tracks` | маршрут: время, статус ACTIVE/COMPLETED/INTERRUPTED, дистанция, число точек и отброшенных фиксов, `last_point_at`, `created_at/updated_at`, `sync_state` | PK `id` (UUID); idx `status`, `started_at`, `sync_state` |
| `location_points` | принятые GPS-точки: lat/lon, `timestamp_utc`, точность, высота/скорость/курс (nullable), источник, радиус исследования, `sync_state` | PK `id` (UUID); FK → tracks (CASCADE); idx (`track_id`,`timestamp_utc`), `timestamp_utc`, `sync_state` |
| `explored_cells` | исследованная территория: (`cell_row`,`cell_col`), `first_visited_at`, `sync_state` | PK (row, col) — он же пространственный индекс; idx `sync_state` |
| `explored_cell_summaries` | производные грубые уровни 4 и 8 для отрисовки при мелком масштабе | PK (level, row, col) |
| `exploration_stats` | одна строка: площадь, число ячеек, `version` (сигнал «территория изменилась») | PK id=0 |
| `sync_metadata` | курсоры pull, статус последней синхронизации, последний аккаунт | PK `key` |

`SyncState.PENDING/SYNCED` хранится прямо в строках и служит локальной очередью изменений: всё PENDING ещё не выгружено.

Геометрия на точку **не хранится**: точка добавляет в множество около 70 целочисленных ячеек (радиус 20 м), повторно посещённые игнорируются.

**Транзакции.** `TrackRepositoryImpl.recordPoint` в одной транзакции проверяет, что трек ACTIVE, вставляет точку, обновляет статистику трека и добавляет ячейки вместе со сводками и `exploration_stats`. Сбой на любом шаге откатывает всё (тест `failure inside recordPoint rolls back the whole transaction`).

**Миграции.** Схема экспортируется (`exportSchema = true`), `DatabaseMigrations.ALL` подключается в билдере. `fallbackToDestructiveMigration` не используется. `MigrationsTest` проверяет, что для каждой версии есть экспортированная схема и миграция с предыдущей.

## GPS: запись и фильтрация

**Поток:** `TrackingService` (foreground, `foregroundServiceType="location"`) → `LocationRepository.locationUpdates(interval)` → `TrackRecorder.onSample` → `LocationFilter` → `RecordLocationUseCase` → `TrackRepository.recordPoint` (транзакция).

- Запись начинается только явной кнопкой (`StartTrackingUseCase`): сначала создаётся ACTIVE-трек в БД, затем стартует сервис. Если сервис не запустился, пустой трек удаляется.
- Дублирование исключено: в БД может быть только один ACTIVE-трек (проверка в транзакции), повторный старт сервиса игнорируется (`recording == null`).
- `START_STICKY`: после убийства процесса система пересоздаёт сервис, и он продолжает ACTIVE-трек. Если старт из фона запрещён (Android 12+ без «Разрешить всегда»), показывается уведомление «Запись прервана». `RecoverTrackingUseCase` при открытии приложения продолжает трек (если пауза < 6 ч) или закрывает его как INTERRUPTED.
- Сторожевой таймер: нет фиксов дольше 45 с → «Нет сигнала GPS»; провайдер выключен → «Геолокация выключена». Запись при этом не останавливается.
- Остановка: кнопка в приложении или в уведомлении → `StopTrackingUseCase` (остановить сервис, закрыть трек, при включённой автосинхронизации запросить sync). Точка, пришедшая после закрытия трека, отклоняется в транзакции (`NotTracking`), запись завершается штатно.
- Адаптивная частота (`LocationRequestPolicy`): если за последнюю минуту ≥4 фиксов лежат в радиусе 10 м и скорость < 0,7 м/с, интервал увеличивается (2→6 с, 4→15 с, 10→30 с). Стоящий на месте пользователь продолжает исследовать территорию.

### Пороги фильтра (`domain/filter/LocationFilterConfig`)

| Правило | Порог | Причина |
|---|---|---|
| Некорректные координаты | NaN/∞, \|lat\|>90, \|lon\|>180, точно (0,0) | мусорные фиксы, «Null Island» |
| Некорректное время | ≤0 или > now + 5 мин | сбитые часы |
| Нет точности / точность хуже | нет `accuracy`, ≤0, или > **40 м** | в городских каньонах GPS даёт 20–40 м; хуже — это уже network-позиция |
| Повтор timestamp | Δt = 0 | повторная доставка |
| Старее предыдущей | Δt < 0 | out of order |
| Слишком часто | Δt < **1 с** | всплески провайдера |
| Идентичные координаты | та же lat/lon и Δt < **30 с** | закэшированный фикс. На месте точка всё равно пишется не реже раза в 30 с |
| Нереалистичный скачок | d > accA+accB и v > **85 м/с** (~300 км/ч) | выбросы. Поезда допустимы |
| Релокация | после **2** последовательных согласованных «скачков» новое место принимается | один плохой «якорь» (или выход из метро) не блокирует запись навсегда |

Расстояние считается по формуле haversine (R = 6 371 008,8 м) между последовательными принятыми точками.

## Fog of War

### Представление территории
Глобальная равноугольная сетка `ExplorationGrid`: шаг **1/20000°** по обеим осям (≈5,56 м по широте; по долготе 5,56·cos φ). Ячейка — (row, col) ∈ [0, 3 600 000) × [0, 7 200 000); столбцы замыкаются на антимеридиане.

Почему именно так:
- географическая сетка, не связанная с пикселями: одинакова на любом zoom и устройстве;
- целочисленные ключи дают дедупликацию бесплатно (PK + `INSERT OR IGNORE`): повторные проходы не растят данные;
- объединение территорий двух устройств — просто объединение множеств (CRDT G-Set), поэтому синхронизация и импорт детерминированы;
- размер ячейки ≈ четверть радиуса 20 м: круг из ~70 ячеек выглядит кругом, а при радиусе 10 м (~16 ячеек) форма ещё различима.

Точка исследует ячейки, **центр** которых лежит в радиусе R (локальная равноугольная проекция; на масштабах ≤100 м погрешность пренебрежима). Ячейка самой точки отмечается всегда.

### Построение геометрии (`ExploredGeometryBuilder`)
1. **Окно.** Видимая область + 50 % запаса. Уровень k выбирается так, чтобы окно было ≤768 ячеек по стороне (ячейка уровня k = 2^k базовых). Уровни 0–3 читаются из `explored_cells` с `>> k`, 4–7 — из сводки уровня 4, ≥8 — из сводки уровня 8. Работа на кадр ограничена при любом zoom: стресс-тест 768×768 со случайными 30 % ячеек — ~0,2 с на JVM.
2. **Трассировка.** Каждая граница «открыта/закрыта» становится направленным ребром (открытая ячейка слева). Рёбра сцепляются в кольца с приоритетом левого поворота: диагонально соседние ячейки дают отдельные кольца без самопересечений (explored — 4-связность, неисследованное — 8-связность). Внешние кольца получаются CCW, дыры — CW.
3. **Вложенность** за O(N): компоненты связности размечаются BFS. Дыра принадлежит внешнему кольцу своей открытой компоненты, остров — дыре, которая граничит с той же закрытой компонентой.
4. **Сглаживание.** Chaikin, 3 итерации, срез четверти ребра, но не более 1 ячейки. Ступеньки становятся кривыми, а длинные границы не «съедаются» (потеря площади только в углах, тест `smoothed area stays close to the cell area`). Тесты `RingValidityTest` проверяют, что кольца не пересекают ни себя, ни друг друга.
5. **Результат** (`ExploredGeometry`): explored-полигоны (подсветка), fog-полигоны (весь мир с вырезанными внешними кольцами + «озёра» внутри исследованного как отдельные полигоны с островами-дырами), все границы (для мягкого края и контура).

Пересчитывается только окно, и только когда камера остановилась (debounce 120 мс) или изменилась `exploration_stats.version`. Вся история GPS на каждом кадре не обрабатывается: точки вообще не участвуют в отрисовке.

### Отрисовка (`ExplorationMapController`)
- Туман — **непрозрачный** `FillLayer` (процедурная бесшовная текстура облаков `fill-pattern` или тёмный цвет) поверх всех слоёв подложки. Исследованное — это дыры в полигоне, поэтому подложка видна ровно там. Это настоящая маска, а не полупрозрачный серый слой.
- Мягкий край — `LineLayer` по границам тумана с `line-blur`, ширина ≈10 м на любом zoom (экспоненциальная интерполяция по zoom). Внутренняя половина размытой линии плавно переходит в открытую карту.
- Explorer Map — те же данные: заливка `fill-opacity 0.32` + контур. Смена режима только переключает `visibility`.
- **Fail-closed обновление.** После каждого `setGeoJson` MapLibre перестраивает тайлы источника и какое-то время его не рисует. Для тумана это открывало бы всю карту на 0,5–1 с; проблема была найдена на эмуляторе. Поэтому туман двухбуферный: новые данные пишутся во второй источник, пока первый продолжает рисоваться. Объединение двух масок закрывает не меньше каждой из них. Старый буфер очищается только на полностью отрисованном кадре (`onDidFinishRenderingFrame(fully=true)`, не раньше 250 мс) или при idle карты. Проверено серией скриншотов во время записи: кадров с открытой подложкой вне исследованного нет.
- До прихода первой геометрии источник тумана содержит весь мир: по умолчанию карта закрыта.

## Приватность и безопасность

- Координаты не пишутся в логи: в `Log.*` попадают только типы ошибок и события.
- `android:allowBackup="false"` и `data-extraction-rules` исключают данные из облачных копий Google и device-to-device переноса. Пользователь переносит данные только явно: экспорт или opt-in синхронизация.
- Только HTTPS: `cleartextTrafficPermitted="false"`. В debug дополнительно доверяются пользовательские CA (для корпоративных прокси), release — только системные.
- Токены Supabase шифруются AES-256-GCM ключом из Android Keystore (`KeystoreSessionStore`). Ключ не покидает Keystore.
- Импорт: копия во внутренний кэш с лимитом 1 ГиБ; лимиты на распакованный размер записи (4 ГиБ) и строки (64 КиБ), белый список имён в ZIP. Архив никогда не распаковывается на диск, поэтому path traversal невозможен. SHA-256 и счётчики каждой части сверяются с манифестом. Каждая запись валидируется до записи в БД.
- Облако: RLS `user_id = auth.uid()` на всех таблицах, у `anon` нет прав, удаление аккаунта через `delete_user()` (SECURITY DEFINER, удаляет только `auth.uid()`).
